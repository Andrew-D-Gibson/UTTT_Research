# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Environment: conda env named `UTTT` (`conda activate UTTT`). Dependencies are just `numpy` and
`tensorflow>=2.9.0` (`requirements.txt`); the installed environment on this machine uses Keras 3
(bundled with TF 2.21), which matters because the code must stay in normal eager-execution style —
Keras 3's save/load format is incompatible with `tf.compat.v1.disable_eager_execution()`.

- **Run training**: `python Project.py` — resumes from `Network.keras` if it already exists (only
  builds a fresh randomly-initialized `convNet` if it doesn't), then runs `TrainingManager().train()`
  for `config['training']['num_of_episodes']` episodes. Each episode only promotes/checkpoints a
  newly-trained candidate if it beats the current champion head-to-head, so `Networks/Episode_N.keras`
  is written sparsely, not every episode (see Architecture below). All hyperparameters (search
  depth, process count, games per episode, training sample size, etc.) live in `Config.py`; there's
  no CLI, edit that file to change run scale.
- **No test suite, linter, or build step exists.** There's no `pytest`/`unittest` usage, no lint
  config. `python Project.py` running one full episode end-to-end (self-play → training → gating →
  eval matches all completing without error) is the closest thing to an integration test.
- **Pretrain from raw MCTS** (optional, fire-and-forget alternative starting point to `Project.py`):
  `python Pretrain.py`. Step 1 builds/resumes a fixed pool of `TrainingExample`s generated by
  network-free MCTS (`GenerateRawMCTSExamples.py`, `MCTS(network=None)` at
  `config['mcts']['pretrain_mcts_depth']`, default 4096) up to `training.max_training_examples`
  examples, saved to `PretrainExamples/pool.pkl` — a no-op once the pool already meets that target,
  so it's safe to rerun or interrupt overnight. Step 2 runs `training.num_of_episodes` rounds of
  training directly against that static pool — no self-play, no candidate/champion gating, every
  round is kept unconditionally — checkpointing every round to `Networks/Pretrain_N.keras` and
  `Network.keras`, logging to `pretrain_log.csv` (same columns as `training_log.csv`). This is a
  one-time bootstrap, not a replacement for self-play: raw MCTS at a fixed depth doesn't get
  stronger no matter how many times its pool is regenerated, so once `pretrain_log.csv`/
  `NetworkTournament.py` show diminishing returns across pool generations, switch to
  `python Project.py`, which resumes from wherever `Network.keras` was left.
- **Elo calibration tool** (separate from the training loop): `python ELO.py` round-robins baseline
  agents (random / rollout-MCTS at various depths) against each other.
- **Network tournament tool** (separate from the training loop): `python NetworkTournament.py`
  snapshots a subsampled ladder of `Networks/Episode_N.keras` checkpoints plus raw-MCTS baselines at
  several depths and runs an Elo round-robin (via `ELO.py`) — checks whether the network actually
  beats plain search, not just whether validation loss is dropping.

## Architecture

See [ARCHITECTURE_OVERVIEW.md](ARCHITECTURE_OVERVIEW.md) for the full component map, per-episode
data flow, and current design details — read it before making non-trivial changes. The load-bearing
patterns that span multiple files and are easy to miss from reading any single file:

- **`Config.py`'s `config` dict is the single source of hyperparameters**, imported via
  `from Config import *` into nearly every other module (`MCTS.py`, `TrainingManager.py`,
  `simulate_self_play_games.py`, `PlayerAgent.py`, ...). There's no per-module configuration —
  changing search depth, process count, or training schedule always means editing `Config.py`.
- **The self-play worker boundary is a full network reload, not shared memory.** `TrainingManager`
  spins up a `multiprocessing.Pool`, and each worker (`simulate_self_play_games.py`) independently
  loads `Network.keras` from disk and runs MCTS entirely on CPU (`CUDA_VISIBLE_DEVICES=-1`) with
  its own single-threaded TF config. Changes to how the network is saved/loaded (e.g. checkpoint
  file extension, format) affect both `TrainingManager.py` (the writer) and
  `simulate_self_play_games.py`/`PlayerAgent.py` (the readers) — Keras 3 requires an explicit
  `.keras`/`.h5` extension on every save path.
- **`MCTS` nodes don't own their own board.** Only the root of an `MCTS` tree holds a real
  `UTTTBoard`; every recursive call during search (`MCTS_iteration`, `random_rollout`,
  `check_network`, `make_children_list`) takes that single shared board as an explicit parameter
  and must pair `board.make_move(...)` with `board.unmake_move()` around any recursive descent into
  a child. Breaking that make/unmake balance (e.g. adding a new recursive path, an early return, or
  an exception between the two calls) silently corrupts the board for every subsequent search — this
  is the single most fragile invariant in the codebase and spans `MCTS.py` and `UTTTBoard.py`
  together.
- **Training gates candidates against the champion; it doesn't always save.**
  `TrainingManager.train()` clones the champion into a *candidate* (`clone_network()` — the
  champion itself is never mutated), trains only the clone, then plays `num_of_testing_games` of
  candidate vs. champion (`agent_match` with `ProbabilisticNetworkMCTSAgent` on both sides — not
  the deterministic `NetworkMCTSAgent`, which would replay identical games in a fixed color order
  and add no signal). The candidate is promoted (and only then does `Networks/Episode_N.keras`/
  `Network.keras` get written) only if it wins at least `self_play.promotion_win_rate` (default
  0.55) of *decisive* (non-drawn) gating games — a bare `wins > losses` majority isn't enough, since
  with `num_of_testing_games` in the tens a 1-2 game margin is statistically indistinguishable from
  a coin flip. A result under that threshold keeps the old champion and skips the checkpoint, so
  `Networks/` ends up sparse (`Episode_0`, `Episode_4`, `Episode_17`, ...), not dense. Outcomes log
  to `gating_log.csv`; training metrics log to `training_log.csv`.
- **Raw-MCTS pretraining (`Pretrain.py`) is a separate pipeline from self-play, sharing only
  `Network.keras` as the handoff point.** `simulate_raw_mcts_games.py` is `MCTS(network=None)`
  (random-rollout evaluation, uniform priors over legal moves) — it deliberately skips
  `worker_utils.configure_cpu_worker()`, since that helper's GPU/thread config calls would force a
  TF import in a worker that otherwise never touches TensorFlow at all, which is also why raw-MCTS
  generation is markedly cheaper per worker-process than self-play/gating despite running many more
  MCTS iterations per move. `GenerateRawMCTSExamples.generate_pool()` is idempotent (a no-op once
  the pool reaches `max_training_examples`), which is what lets `Pretrain.py` call it unconditionally
  as step one of a single unattended run. `PretrainManager.pretrain()` then trains `Network.keras`
  in place each round — no `clone_network()`, no gating, since there's no opponent to gate against —
  and checkpoints to `Networks/Pretrain_N.keras` every round rather than sparsely.
  `NetworkTournament.py`'s checkpoint discovery (`discover_checkpoints`/`snapshot_checkpoints`/
  `build_network_specs`) takes a `prefix` parameter so it ladders both `Episode_*` and `Pretrain_*`
  checkpoints side by side. Like `Episode_N`, `Pretrain_N` numbering restarts at 0 every `Pretrain.py`
  run, so re-running it after switching pools can silently overwrite the previous run's checkpoint
  files (`Network.keras` itself always holds the latest weights regardless).
- **A "fresh" run is often actually a resume.** `Project.py` only builds a new `convNet` if
  `Network.keras` doesn't exist, and `TrainingManager.__init__` separately loads the
  most-recently-modified file in `TrainingExamples/` (by mtime, not the highest `Episode_N` —
  numbering restarts at 0 every run) as the starting replay buffer, keeping it under one fixed
  backup name (`TrainingExamples/_resumed_from.pkl`) and deleting every other file. `python
  Project.py` is only really starting from scratch if both `Network.keras` and `TrainingExamples/`
  are absent/empty.
- **Board bit layout is row-major but visually flipped.** `UTTTBoard`'s `x`/`o`/eligible-subboard
  bitboards index cells as `move = subboard*9 + local_cell` (both subboard and local_cell in
  standard row-major 0-8 order), but `symbol_array_representation()`'s output array is that layout
  with both axes reversed (`[::-1, ::-1]`) to match the orientation `print()` and the network's
  training data have always used. Any new code reading/writing the bitboards directly (not through
  `get_array_representation()`) needs to reason in the *unflipped* row-major indexing; anything
  consuming the `(9,9,4)` array tensor sees the *flipped* orientation.
